# Review Standard

## 评审顺序

1. 固定范围与基线：确认 diff、提交、路径、目标行为和非目标。
2. 选择角色：按审查范围形成 `rolePlan`，只激活命中前端、后端、QA、产品或 UI 领域的角色。
3. 需求符合性：是否实现了约定范围。
4. 行为正确性：从调用链构造核心路径、异常和边界反例。
5. 风险控制：安全、兼容、性能、数据和发布风险。
6. 代码质量：可读性、复用、测试和维护。

## 发现契约

每个发现必须包含：

- 严重度：P0/P1/P2/P3。
- 代码位置：文件与行范围，或明确的调用路径。
- 失效场景：什么输入、状态或环境会触发。
- 证据：代码、测试、日志、规格或可重复推理。
- 建议动作：最小修复、优化或明确不修改的理由。
- 验证方式：修复后应运行的测试、命令或人工路径。

没有发现时，也必须写明已检查范围、检查维度和未覆盖范围。
未激活领域必须写明不适用依据，不得被表述为已审查无风险。

## 必查项

- 是否有无关改动。
- 是否遗漏验收标准。
- 是否有硬编码凭据、环境或权限绕过。
- 是否引入跨端或跨业务功能泄漏。
- 是否有失败测试或未解释的跳过测试。
- 是否把静态检查误写成运行时行为验证。
- 是否存在与当前审查范围无关的重构建议。

## 结论

评审结论使用：

- `通过`。
- `修改后通过`。
- `不通过`。

结论必须附带阻塞项和建议修复顺序。

P0/P1 发现未关闭时不得给出“通过”或“带风险通过”。
