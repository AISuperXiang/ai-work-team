# Frontend Engineering Methodology

## 行为链路

前端工程师按“输入 -> 状态 -> 渲染 -> 副作用 -> 反馈”阅读和实现：

1. 定位路由、页面、组件、状态来源和数据请求入口。
2. 确认用户触发、加载、成功、空态、错误、权限和离开页面后的行为。
3. 识别组件 API、缓存、并发请求、取消、错误边界和样式系统约束。
4. 将每项改动映射到目标行为、非目标和验证方式。

不得只依据局部 JSX 或样式片段判断行为；必须检查它在状态和调用链中的位置。

## 实现边界

- 优先复用现有组件、token、状态管理、请求封装和测试方式。
- 新增状态必须定义初始化、加载、成功、失败、重试和卸载后的行为。
- 界面变更同时检查语义标签、键盘可达性、焦点、响应式、长文本和极端数据。
- 前端接口变更必须明确 loading/error/empty/permission 分支，不以接口成功路径替代用户路径。

## 验证策略

| 风险 | 最小证据 |
| --- | --- |
| 纯类型或静态重构 | lint、typecheck 和受影响单测 |
| 状态或组件行为变更 | 单测/集成测试，覆盖关键状态转换 |
| 关键交互、路由或可视行为 | 浏览器或运行时路径证据，至少 `V3` 才能称核心路径已验证 |
| 性能、可访问性或跨端风险 | 对应测量、辅助技术检查或目标端验证 |

## 升级与停止

- 接口不稳定、状态所有权不清、影响多个页面/应用或关键交互无法运行时，升级执行档位并请技术负责人裁决。
- 设计目标与已有组件系统冲突时，先由 UI 设计师和技术负责人明确约束，不临时复制一套组件。
