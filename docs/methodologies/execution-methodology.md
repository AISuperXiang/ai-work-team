# Execution Methodology

## 目标

用与风险、未知度和变更影响相匹配的流程完成任务。角色、文档和并行执行必须增加可验证信息；不得为了形式完整而制造重复产物。

## 执行档位

开始任何实现、修复或代码审查前，交付经理和技术负责人按以下信号选择 `executionProfile`，并写入 `workflow-status.json`：

| 档位 | 适用条件 | 最小产物 | 不可省略项 |
| --- | --- | --- | --- |
| `lightweight` | `S` 级、单一有界模块、可逆、无数据/权限/公开接口/跨端影响 | 权威状态、必要证据和可读结论；决定/风险/交接可内联引用 | 真实代码阅读、目标行为、变更范围、回归验证、结论边界 |
| `standard` | 默认；多模块、行为不确定、需要产品或 QA 判断 | 权威状态、必要方案/契约原文和证据；摘要单向派生 | 决策、交接、测试策略和证据索引 |
| `assurance` | `L/XL`、安全/资金/权限/数据迁移、外部副作用或高回滚成本 | 标准产物加里程碑、灰度、回滚、监控和复盘计划 | 独立风险评审、运行时验证、发布准入和责任人确认 |

出现任一条件时必须从 `lightweight` 升级：影响范围扩大、复现失败、修改公开契约、引入并发/数据迁移/权限变化、验证失败或发现 P0/P1 风险。紧急程度不能降低档位。

`deliveryControl.recordPolicy` 记录产物档位、唯一权威记录、派生摘要和有依据的省略项。
减少独立文件不等于减少信息；业务要求、required checks、风险、审批和责任仍须可追溯。
数字质量评分默认不生成，仅在用户要求、复盘或同类方案比较时作为辅助。

## 角色与并行

- 默认由当前 Agent 顺序执行角色判断，避免把同一份代码阅读重复分发。
- 只有评审维度相互独立、输入已冻结且不会修改同一文件时才并行，例如技术风险与 QA 测试策略。
- 并行子 Agent 必须有问题边界、只读或独占文件边界、预期证据和返回契约；不能以多数意见替代证据。
- 实现代码默认由一个负责人修改。发现冲突或接口分歧时，停止并行，先由交付经理裁决。
- 共享源码、worktree 构建目录、浏览器会话、账号和可变 fixture 必须遵守项目真实资源锁；
  状态中的 owner 只是记录，不是原子锁。

## 证据与结论上限

`verificationLevel` 记录当前最高验证等级：

| 等级 | 证据 | 允许结论 |
| --- | --- | --- |
| `V0` | 未验证或仅推理 | 仅能说明设计或假设，不得称已修复 |
| `V1` | 格式、lint、typecheck、静态审查 | 可称静态检查通过，不得称关键行为已验证 |
| `V2` | 单测、集成测试或可重复脚本 | 可称受测行为通过，明确未覆盖范围 |
| `V3` | 运行时、浏览器或端到端关键路径 | 可称核心路径已验证，保留环境差异风险 |
| `V4` | 生产灰度、真实验收或上线观测 | 可称交付/收益已验证，附数据来源和时间 |

验证缺失时降低结论，不伪造通过。复现失败的缺陷只能交付为“待定位/待采证”，并给出最小插桩或数据采集计划。

`verificationLevel` 是汇总标签，不是覆盖关系。v2 任务按
[Delivery Controls](../delivery-controls.md) 分别核对 required check 的方法、分支、环境和快照：
浏览器 V3 不能替代另一个未运行的单测或真实设备项，分析报告完成也不能替代实现验收。

## 常见失败样例

- 用 lint、typecheck 或代码阅读代替浏览器/运行时结果，并在交付中称“已验收”。
- 为单文件、可逆改动创建全部角色文档，产物没有增加任何决策或验证信息。
- 多个角色并行修改同一代码区域，最后通过合并意见而不是调用链证据裁决冲突。
- 无法复现缺陷时直接提交修复，没有保留复现条件、插桩计划和未覆盖风险。

## 完成检查

在阶段完成前确认：

1. 当前档位仍匹配真实风险。
2. 每个已完成结论都有对应证据和验证等级。
3. 角色输出已经转成可执行决策、变更或测试项。
4. 未覆盖范围、失败条件和回滚路径已被保留。
5. 当前 invocation 未超出授权，impact scope 与环境 probe 仍匹配本轮结果。
