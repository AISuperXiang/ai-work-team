# Goal-Driven Technical Design Methodology

## 目标

把一个方向性目标转成经过需求、体验、工程和 QA 评审的可执行设计包。设计包既允许模型补齐低风险细节，也通过契约、预算、门禁和停止条件限制战略漂移与无限迭代。

本方法论服务 `/team goal-design`，不替代 `/team build`。设计阶段不修改目标项目代码。

## 目标收敛

产品经理先把目标写入 `goal-contract.json`：

- 目标陈述描述可观测结果，不只描述功能。
- 目标用户、当前问题、期望结果和非目标明确。
- 每个期望结果至少关联一个指标。
- 指标包含基线、目标、数据来源和观察周期。
- 约束覆盖战略、时间、预算、技术、安全与合规。
- 未证实判断进入 `assumptions`，并有最小验证方法。
- 目标、约束或关键假设变化时触发重新评审。

缺少数据时可以使用“待采集基线”，但必须给出采集方式、负责人和最晚决策点。

## 从目标到 PRD

目标合同稳定后，产品经理和运营经理将其展开为 PRD：

1. 定义核心用户场景和用户故事。
2. 将范围分为 must、should、could 和 out of scope。
3. 为 must 项定义“前置条件 -> 动作/输入 -> 可观察结果 -> 证据”。
4. 把成功指标映射到需求验收、上线观测和复盘。
5. 标记影响技术架构、UI、权限、数据或发布的约束。

PRD 不能增加与 `goal-contract.json` 冲突的目标。确需改变目标时，先更新目标合同并重新评审。

## 条件式 UI 评审

- 页面、组件、文案、交互、可访问性或响应式发生变化时，UI 设计师为 `active`。
- 只需复用既有设计约束时，UI 设计师为 `consulted`。
- 无界面影响时为 `not_applicable`，在 `rolePlan` 和技术方案中记录依据。

UI 评审输出必须能转成模块、状态、任务验收和 QA 测试点。

## 技术方案构建

技术负责人按以下顺序形成初稿：

1. 建立事实、假设、调用链、接口、数据、权限和测试能力清单。
2. 按用户或业务结果定义纵向里程碑，不按前端、后端、数据库等技术层横向切割。
3. 拆解核心模块、接口、数据和复杂状态转换。
4. 比较保留现状、最小变更和新增抽象，记录成本、收益、风险、兼容与验证成本。
5. 把推荐方案拆成 Task DAG，明确依赖、关键路径、并行边界、文件所有权和验证证据。
6. 定义计划迭代轮数、最大迭代轮数、每轮退出条件、停止和重规划规则。
7. 将所有自动执行权限制在 `autonomy-policy.json` 内。

## 四类契约

### Goal Contract

使用 `schemas/goal-contract.schema.json`。它是目标、价值和约束的唯一基线。下游产物不得静默修改目标。

### Milestone

使用 `schemas/milestone.schema.json`：

- 每个里程碑交付一个可独立验证的纵向结果。
- `plannedIterations` 不得大于 `maxIterations`。
- 依赖必须引用已存在里程碑，且不得自依赖或成环。
- 每个里程碑包含交付物、Task、退出条件和目标验证等级。

### Task

使用 `schemas/task.schema.json`：

- Task 必须属于一个里程碑。
- 依赖必须引用已存在 Task，且不得自依赖或成环。
- 输入、输出、验收、证据、责任能力、文件所有权和重试策略明确。
- 并行 Task 不得拥有重叠文件或未冻结的共享契约。
- 重试耗尽后只能阻塞、升级或重规划，不能静默继续。

### Autonomy Policy

使用 `schemas/autonomy-policy.schema.json`：

- `plannedIterations`、`maxIterations` 和 `maxDesignReviewRounds` 为硬上限。
- 自动决策只覆盖可逆、低风险、预算内且有验证的实现细节。
- 改变目标、范围、公开契约、预算或高风险边界必须审批。
- 生产、删除、付费、权限、凭据、安全、隐私和合规操作必须审批。
- 达成目标、预算耗尽、连续无改进、风险超阈值或人工停止必须触发停止规则。

## 评审与修订

技术方案使用两级评审：

1. **Technical Review**：技术负责人、命中领域研发和 QA 评审架构、接口、数据、风险、可测性、任务图和自治契约。
2. **Cross-Role Review**：产品、适用 UI 和 QA 回审技术方案是否保持目标、范围、体验与验收一致。

每条意见必须有证据、严重度、处置和复核。技术负责人统一修改方案，其他角色不并行写 `technical-design.md`。

处置规则：

- `accepted`：必须更新方案或契约并复核。
- `rejected`：必须说明事实依据和反例为何不成立。
- `deferred`：必须说明延期影响、责任人和触发条件。
- `needs_user_decision`：整理为最多 3 个带影响的决策项。

达到最大评审轮数仍未收敛时停止自动修订，不得自行扩大轮数。

## 决策交付

最终产物必须回答：

- 为什么值得做，什么不做。
- 推荐哪种技术方案，为什么。
- 核心模块和复杂逻辑如何工作。
- 分几个里程碑、计划几轮、最多几轮。
- 每个 Task 的输入、输出、依赖、责任和证据是什么。
- 哪些决策可自动做，哪些需要通知或审批。
- 何时继续、重规划、暂停或停止。
- 用户批准后如何进入 `/team build`。

最终状态是“方案已评审，等待用户批准执行”。没有代码、运行时或生产证据时，验证等级不得超过 `V1`。
