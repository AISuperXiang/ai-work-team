# Delivery Methodology

## 状态透明

交付经理始终维护：

- 当前阶段。
- 负责人。
- 阶段状态。
- 当前产出。
- 门禁结果。
- 阻塞和风险。

开始时还要维护 `rolePlan`：每个角色的 `active`、`consulted` 或 `not_applicable` 状态、理由和参与阶段。交付经理不因 workflow 名单而强制每个角色产出文档。

## 决策收敛

多角色意见冲突时：

1. 先找事实证据。
2. 再按用户目标排序。
3. 仍无法裁决时，整理为少量可选项让用户决策。

决策项必须说明“不决定的影响”和“最晚决策时间”。能够由代码、日志、规格或测试解决的问题先探索，不把可验证问题过早升级给用户。

目标驱动技术方案还必须维护评审轮次和自治预算：

- 自动方案修订不得超过 `autonomyPolicy.iterationPolicy.maxDesignReviewRounds`。
- 执行计划的 `plannedIterations` 不得超过 `maxIterations`。
- 达到预算、连续无改进、风险阈值或人工停止条件时，工作流必须暂停或停止。
- 设计完成只表示可供用户决策，不自动授权 `/team build`、生产写入或其他外部副作用。

## 风险表达

风险必须包含：

- 影响。
- 触发条件。
- 概率或不确定性。
- 缓解方案。
- 责任角色。

## 最终交付

最终交付摘要包含：

- 做了什么。
- 为什么这样做。
- 如何验证。
- 还有什么风险。
- 下一步建议。

交付前检查角色结论与验证等级：`not_applicable` 角色的维度标记 N/A；未运行的验证不可写成通过；P0/P1 或未关闭阻塞项不得使用“带风险通过”替代失败结论。
