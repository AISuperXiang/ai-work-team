# QA Methodology

## 从验收标准反推用例

每条验收标准至少对应一个测试场景。若验收标准不可测试，先反馈产品经理补齐。

QA 在存在行为变更、缺陷修复、发布风险或回归影响时设为 `active`。仅输出设计草案且没有待验证行为时可为 `consulted` 或 `not_applicable`，但必须记录由谁承担验证计划。

## 场景分类

- 正常路径。
- 异常路径。
- 边界数据。
- 权限和角色。
- 兼容和响应式。
- 回归影响面。

## 风险驱动测试

先列出“最可能失效且影响最大的路径”，再选择测试层级：

| 风险 | 优先证据 |
| --- | --- |
| 纯逻辑或状态转换 | 单元测试 |
| 接口、数据或跨模块契约 | 集成测试 |
| 关键用户交互或浏览器状态 | 运行时、浏览器或 E2E 证据 |
| 无法自动化的体验路径 | 可重复的手工步骤、环境、截图或录屏说明 |

每项未覆盖风险必须说明原因、影响、下一步和对应的 `verificationLevel`，不能用测试数量代替关键路径覆盖。

## 目标驱动方案评审

在 `/team goal-design` 中，QA 作为 `consulted` 或 `active` 角色检查：

- Goal Contract 的成功标准是否可观测、可测试并能关联证据。
- 每个里程碑退出条件是否能通过明确环境、数据、命令或人工步骤验证。
- 每个 Task 的验收标准、证据要求和目标验证等级是否匹配风险。
- Task DAG 是否保留测试前置条件、测试数据、环境准备和回归任务。
- 自治策略是否在验证失败、连续无改进、重试耗尽或 P0/P1 风险时停止或升级。
- 方案阶段只有静态证据时是否将结论限制在 `V0-V1`。

QA 评审不执行未来实现的测试，但必须给出可执行测试入口和未覆盖风险；无法设计验证路径的里程碑不得进入用户批准状态。

## 用例字段

- 场景名称。
- 前置条件。
- 输入数据。
- 操作步骤。
- 期望结果。
- 优先级。
- 自动化或手工。
- 结果和证据。

## 缺陷闭环

缺陷必须包含：

- 复现步骤。
- 实际结果。
- 期望结果。
- 环境和数据。
- 影响范围。
- 严重级别。
- 复测结论。

缺陷未复现时，QA 输出最小采证计划而不是猜测根因；修复后必须复跑同一证据路径，才能把结论提升为“受测行为通过”或更高等级。
