# Product Methodology

## 目标契约

产品经理先把需求转成目标契约：

- 用户：谁在什么场景使用。
- 问题：当前痛点或机会。
- 结果：用户和业务分别得到什么。
- 成功标准：如何证明完成。
- 非目标：本次不解决什么。

使用 `/team goal-design` 时，目标契约必须落到 `goal-contract.json`，并满足 `schemas/goal-contract.schema.json`。期望结果、指标、成功标准和假设必须通过 id 显式关联；目标、核心价值、非目标或战略约束发生变化时，先更新目标契约并重新评审，不能只修改下游 PRD。

先按 `role-activation-methodology.md` 判断是否需要产品角色。纯内部重构、已有明确期望行为的技术修复或仅代码风格审查，可将产品经理标记为 `not_applicable`；若缺陷影响范围、用户预期或验收标准不明确，必须升级为 `active`。

## 范围裁剪

按 must / should / could / out of scope 分类：

- `must`：没有它需求不成立。
- `should`：重要但可延期。
- `could`：锦上添花。
- `out of scope`：明确排除，防止需求膨胀。

## 验收标准

验收标准必须满足：

- 可观测。
- 可测试。
- 有输入和期望结果。
- 包含异常和边界。

每条标准采用“前置条件 -> 用户动作/系统输入 -> 可观察结果 -> 证据”的格式。无法写成这个格式时，不能把它交给研发或 QA。

## PRD 最小结构

- 背景和目标。
- 用户与场景。
- 范围和非范围。
- 用户故事。
- 功能规则。
- 状态和异常。
- 验收标准。
- 风险和开放问题。

## 决策与停止条件

- 价值指标可标记为待采集假设，但必须说明采集方式、负责人和触发复审的阈值。
- 模型可以补齐可逆、低风险的需求细节，但不得静默改变目标用户、核心价值、预算、风险边界或成功指标。
- 用户目标、范围或验收存在冲突时，输出不超过 3 个可裁决选项，不自行选择高影响取舍。
- 不把“功能已开发”当成产品完成；产品结论必须引用验收结果和未覆盖范围。
