# Role Activation Methodology

## 目标

角色是为决策、实现或验证服务的，不是每个任务都必须参与的固定清单。每次工作流开始前，交付经理和技术负责人必须形成 `rolePlan`，再加载对应成员和方法论。

## Role Plan 契约

每个被评估的角色必须记录：

| 字段 | 要求 |
| --- | --- |
| `role` | 已注册的成员 id。 |
| `mode` | `active`、`consulted` 或 `not_applicable`。 |
| `reason` | 触发信号、审查范围或不适用原因。 |
| `stages` | 该角色实际参与的阶段；`not_applicable` 为空数组。 |

- `active`：对阶段产出、决策、代码、测试或门禁有直接责任。
- `consulted`：只在有界问题上提供结论或证据，不拥有完整阶段产出。
- `not_applicable`：已判断无关，不创建虚假的文档、评分或交接。
- `standard` 和 `assurance` 默认激活 `delivery-manager`；`lightweight` 可以由交付负责人兼任，但仍要记录责任归属。
- 角色从 `not_applicable` 或 `consulted` 升级为 `active` 时，必须更新 `rolePlan`、状态板和交接记录。

## 场景矩阵

| 角色 | 设为 `active` 的信号 | 可设为 `consulted` 的信号 | 常见 `not_applicable` 场景 |
| --- | --- | --- | --- |
| 产品经理 | 用户可见行为、范围、验收或期望行为不清 | 缺陷影响需确认 | 纯内部重构且现有行为明确 |
| 运营经理 | 指标、实验、运营配置、发布节奏或用户触达受影响 | 需要收益观测口径 | 无用户/业务指标变化的工程修复 |
| UI 设计师 | 界面、交互、文案、可访问性或响应式发生变化 | UI 走查或设计约束解释 | 纯服务端、数据或无界面逻辑改动 |
| 技术负责人 | 跨模块、公开契约、架构、权限、迁移、并发或高风险变更 | 对单模块方案做风险复核 | 已有明确模式的低风险局部改动 |
| 前端工程师 | 浏览器、客户端状态、页面、组件或前端构建受影响 | 客户端兼容性评审 | 无客户端代码、配置或行为影响 |
| 后端工程师 | API、服务、任务、数据库、权限或数据一致性受影响 | 接口/数据契约评审 | 无服务端代码、接口、配置或数据影响 |
| QA 工程师 | 用户行为、缺陷修复、发布风险或回归范围需要验证 | 测试策略和证据充分性复核 | 仅产出不可执行设计草案，且无待验证行为 |
| 交付经理 | `standard` / `assurance` 任务、跨角色决策、风险或证据交付 | `lightweight` 的状态与结论复核 | 不适用；但可与单一负责人合并执行 |

## 工作流最小组合

| 工作流 | 默认最小激活组合 | 按信号追加 |
| --- | --- | --- |
| 端到端需求交付 | 交付经理、产品经理、技术负责人、QA | UI、运营、前端、后端 |
| 目标驱动技术方案 | 交付经理、产品经理、技术负责人、QA | 运营、UI、前端、后端 |
| 技术方案评审 | 技术负责人、QA、交付经理 | 前端、后端、产品、UI |
| 缺陷修复 | 交付经理、问题归属研发、QA | 产品、技术负责人、另一端研发 |
| 代码审查 | 技术负责人、命中领域研发 | QA、产品、UI、后端或前端 |
| 产品/UI/QA 走查 | 交付经理、产品经理、QA | UI、技术负责人 |

## 选择规则

1. 先根据变更或问题的用户可见性、技术边界、风险和验证需求选择角色，再读取成员文件。
2. 同一角色只有在能贡献新的决策、证据或实现时才保持 `active`。
3. 不能因为角色未参与就跳过对应领域风险；必须在 `rolePlan.reason` 中说明为何不适用。
4. `assurance` 任务的权限、数据、安全、迁移、灰度和回滚风险必须由技术负责人或明确的领域负责人复核。
5. `P0/P1`、验证失败、复现失败、范围扩大或跨端影响会触发重新评估 `rolePlan`。

## 完成检查

- `workflow-status.json.rolePlan` 与阶段 owner 一致。
- 已激活角色的输出、证据和门禁可追溯。
- 未激活角色有明确不适用依据，最终评分对应维度标为 `N/A` 或不纳入。
- 角色结论冲突时已由交付经理记录裁决，而不是通过增加更多角色投票解决。
