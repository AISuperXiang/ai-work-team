# Quality Rubrics

本文件把“有价值、先进、健壮、美观、可交付”转成可检查标准。端到端实现、缺陷修复和 UI 走查必须使用本评分。

业务影响维度的独立细则见 [`business-impact-rubric.md`](business-impact-rubric.md)。当本文件与业务影响细则冲突时，以 `business-impact-rubric.md` 的最低线为准。

## 评分规则

每项 0-5 分：

- 0：未处理。
- 1：有口头说明，无落地证据。
- 2：基本可用，但遗漏明显边界。
- 3：满足当前需求，有基础验证。
- 4：质量较好，覆盖关键边界和回归。
- 5：高质量，设计清晰、验证充分、风险闭环。

交付最低线：

- 新功能的业务影响 >= 4；缺陷修复和纯代码审查必须说明影响范围、严重度和用户/业务风险，未涉及业务指标时可标记 N/A。
- 技术先进性 >= 3。
- 健壮性 >= 4。
- 测试可信度 >= 4。
- UI 美观与可用性：涉及 UI 时 >= 4；不涉及 UI 时标记 N/A。
- 安全与兼容性 >= 4。
- 交付完整度 >= 4。
- 任何 P0/P1 风险不得交付。

评分前必须读取 `workflow-status.json` 中的 `executionProfile` 与 `verificationLevel`。评分不能抬高验证结论：`V1` 静态检查通过时，测试可信度最高为 3；没有运行时或等价证据的核心交互不得按“已验收”评分。

评分还必须读取 `rolePlan`。只有对应领域角色为 `active` 或存在可追溯证据时才给该维度打分；与当前范围无关的 UI、运营或业务影响维度标记为 `N/A`，并在交付摘要中记录不适用原因。

## 业务影响

本维度必须同时满足 [`business-impact-rubric.md`](business-impact-rubric.md) 的必填输入和阻断规则。

检查：

- 是否明确目标用户、价值假设和核心收益。
- 是否定义指标基线、收益目标、观测周期和数据来源。
- 是否说明成本收益比，包括研发投入、运营投入、维护成本和预期回报。
- 是否有上线后观测结果；未上线时必须有可执行观测计划和复盘口径。
- 是否把增长、效率、成本、风险或用户价值映射到 PRD、测试和交付摘要。

高分标准：

- 价值假设可被数据或用户行为验证。
- 指标口径清楚，收益目标和成本边界可追踪。
- 交付后能直接进入观测、复盘或下一轮产品决策。

低分阻断：

- 只描述功能，不说明用户价值或业务收益。
- 没有指标基线、收益目标或观测方式。
- 用模糊表述替代可验证指标，例如“提升体验”但没有判断口径。

## 技术先进性

检查：

- 是否使用项目当前推荐架构、框架和组件模式。
- 是否避免过时 API、临时 hack 和重复造轮子。
- 是否有清晰模块边界和可演进接口。
- 是否对新抽象给出必要性说明。

高分标准：

- 方案顺应现有架构，同时减少真实复杂度。
- 新增抽象有明确复用点或隔离收益。
- 不牺牲可读性追求“炫技”。

## 健壮性

检查：

- 输入校验、异常、空态、权限、超时和失败路径。
- 并发、幂等、重试、回滚或降级。
- 数据一致性和兼容性。
- 多端、多 App 或多环境影响。

高分标准：

- 关键失败模式都有处理。
- 变更对旧用户、旧数据和旧配置兼容。
- 出错时有可诊断信息，不泄露敏感信息。

## UI 美观与可用性

检查：

- 信息层级、布局节奏、视觉一致性。
- 响应式、可访问性、长文本、极端数据。
- 动效和交互反馈是否服务任务。
- 是否符合现有设计系统或明确设计方向。

高分标准：

- 首屏重点明确，用户路径自然。
- 状态完整，异常和空态不突兀。
- 视觉细节精修但不牺牲可读性和性能。

## 测试可信度

检查：

- 验收标准是否逐项映射到测试。
- 是否覆盖正常、异常、边界、权限和回归。
- 是否有命令、步骤、数据和结果。
- 失败是否复现、修复、复跑。

高分标准：

- 自动化覆盖核心逻辑。
- UI 或复杂交互有浏览器/人工验证证据。
- 剩余未测范围被明确说明。

验证等级参考：

- `V1`：lint、typecheck、静态审查，只能证明静态约束。
- `V2`：单元或集成测试，可证明受测行为。
- `V3`：浏览器、运行时或端到端验证，可证明关键用户路径。
- `V4`：灰度、真实验收或上线观测，可证明交付后的行为或收益。

缺陷修复必须通过 `reproduction-gate`，代码审查必须通过 `review-gate`；二者都不能以“未发现问题”替代证据。

## 安全与兼容性

检查：

- 无硬编码密钥、Token、Cookie、内部凭据。
- 权限、鉴权、审计、敏感数据脱敏。
- 破坏性变更是否有迁移和回滚。
- 错误信息是否避免泄露内部细节。

高分标准：

- 安全风险在设计阶段即被消除。
- 兼容策略清晰，有验证证据。

## 交付完整度

检查：

- workspace 需求目录是否完整。
- PRD、技术方案、实现计划、测试计划、走查报告、交付摘要是否落盘。
- 变更文件和验证结果是否可追溯。
- 产品、UI、QA 是否给出明确结论。

高分标准：

- 用户无需追问即可知道做了什么、如何验证、还有什么风险。
